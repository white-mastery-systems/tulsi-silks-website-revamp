Negative Stock Investigation

Why "Yellow Soft Silk Saree" (SKU TE111935) dropped to -1 stock and kept selling

Project: Yourstore · Reported by: client (Tulsi Silks) · Status: Root cause confirmed — frontend fix done (website), backend fix pending

1. What happened

This product only ever had 1 unit in stock. Stock dropped to -1, and even after that, the website kept letting customers order and pay for it. There are two separate bugs behind this, not one:

  1. Why stock went negative — the same checkout was submitted twice by one customer, and nothing stopped the second one from deducting stock that was already gone.
  2. Why it kept being orderable afterward — the website's "Add to Cart" / "Buy Now" buttons, and the Cash-on-Delivery checkout itself, never actually check whether stock is above zero.

The first two orders were checked against customer_id, session_id, client_ip_address, and userAgent — every field matched exactly. Same person, same phone, same checkout session, 54 seconds apart. The third order was checked the same way and belongs to a completely different, unrelated customer.

The third order on 2026-11-24 is the one the client noticed ("we received an order today"). It did not cause the negative stock — stock was already -1 four days earlier. It only exposed the problem.

3. Cause 1 — how stock went negative

Customer taps "Place Order" (1st request) ↓ Order created → stock deducted immediately (does not wait for payment) ↓ Customer taps "Place Order" again, 54 seconds later (2nd request) ↓ A second order is created → stock deducted again ↓ Nothing checked "is there still stock left?" before either deduction ↓ Result: stock goes 1 → 0 → -1

Two things had to be true for this to happen:

  • Stock is deducted the moment an order is created — not only when payment is confirmed. So even an unpaid, duplicate order still reduces stock.
  • The deduction has no floor — it never checks "is stock still enough" before subtracting, so it can go below zero with no warning or block.

4. Cause 2 — why it kept showing as orderable on the website

This is a separate bug from Cause 1, found by checking the storefront product page and the Cash-on-Delivery checkout:

WhereWhat's wrong
"Buy Now" button Has no stock check at all. It's only disabled while a request is in progress — never based on the actual stock number.
"Add to Cart" button Does have a stock check, but a separate line of code silently reduces the requested quantity down to match whatever stock is — even when stock is negative. After that adjustment, the check always passes, so the button shows as available no matter how negative stock gets. There's also no "Out of Stock" message shown in its place.
Cash-on-Delivery checkout Creates the order and deducts stock directly — it never asks "is there enough stock" at all. The real stock check only exists on the online prepaid (card/UPI) checkout path, and even there it only runs once, early, when the cart is first built — not again when the order is actually placed.
Net effect: once stock goes negative for any reason, nothing on the website or in Cash-on-Delivery checkout stops the next customer from ordering and paying for it too — which is exactly what happened on 2026-11-24.

6. What needs to change

#FixBackendFrontend
1 Add a floor to the stock deduction — it should only succeed when enough stock remains, otherwise fail cleanly instead of going negative Required —
2 Add a stock check to Cash-on-Delivery checkout, and re-run the stock check at the moment an order is created on every checkout path — not just when the cart was first opened Required —
3 Fix the Add to Cart / Buy Now buttons to actually check stock, and show "Out of Stock" instead of letting a negative-stock product render as normal — Required — product page buttons
4 Prevent duplicate order creation from the same checkout (double-click / retry) Required — reject a repeat order if the same cart/session submits again within a few seconds Recommended — disable the "Place Order" button immediately on click
5 Deduct stock once per order (mark the order as "stock already deducted") Required —
6 Block negative values on the admin Stock field — Required — Admin Panel product edit screen

7. Scope of the fix

ChangeTouchesRisk to other stores
Floor on stock deduction Shared stock-update function None — makes the existing update safer everywhere it runs; normal in-stock orders are unaffected
Stock check on COD + re-check at order creation Order creation step None — only blocks orders that are already invalid
Add to Cart / Buy Now stock check Product page buttons only None — only affects display/enabling of buttons for out-of-stock items
Duplicate order prevention Checkout submission handling None — only blocks an immediate repeat of the same cart/checkout, not separate legitimate orders
Once-per-order deduction Payment callback handlers None — skips only duplicate calls, never the first valid one
Admin field guard Product edit screen only None — single input validation
Every change is scoped to the stock/order logic itself and does not touch any other store or workflow sharing the same codebase.

8. Fix done in the website code

Repository: tulsi-silks-website-revamp (Angular storefront). These cover frontend items #3 and #4 from section 6. Items #1, #2 and #5 are backend, and #6 is in the Admin Panel. None of those are part of this change.

Correction to section 4: in this storefront the Add to Cart and Buy Now buttons were already hidden when stock is below the minimum quantity (default 1). The main product section then shows "SOLD OUT". The gaps that remained are listed below. The product page always loads fresh stock in the browser, because the product details request is a POST and is not reused from the server render.

A. Duplicate order from the COD popup (item #4, frontend part)

FileChange
src/app/views/checkout/product-order-details/product-order-details.component.html The two Place Order buttons in the Cash-on-Delivery popup (with and without OTP) are now [disabled]="orderForm.submit" and show a spinner. Before, only the payment list buttons were disabled, so the popup button could be tapped again while the first order request was still running.
…/product-order-details.component.ts — onMakePayment() Returns immediately if orderForm.submit is already true. This also blocks pressing Enter more than once on the OTP form.
…/product-order-details.component.ts — continuePlaceCodOrder() Added an error handler to the COD CREATE_ORDER call. If the network request fails, the page unlocks and shows "Unable to place the order. Please check your orders before trying again." Before, it stayed on the loader.

B. Product page stock checks (item #3)

FileChange
src/app/views/product/product.component.ts — new hasStockForSelection() Returns true only when stock covers the minimum quantity and the selected quantity. addtoCart() and buyNow() now call it first. If it fails, they stop and show "This product is out of stock".
product.component.ts — 5 quantity adjustments Where the quantity is reduced to match stock (page load, variant change, customization, incQty()), it now uses Math.max(0, …). The quantity can no longer become negative when stock is negative.
src/app/views/product/product.component.html The compact (sticky) button bar now shows a disabled "Out of Stock" button when stock is below the minimum and pre-order is off. Before, that area was empty. Also added the out_of_stock alert message.
What the website fix cannot do alone: it blocks fast double taps and buttons on a product that is visibly out of stock. It cannot stop a repeat order sent ~1 minute later (the 54-second gap in this incident), or a tab that was opened while stock was still 1. Those need backend fixes #1, #2 and #4 (reject when stock is not enough, and reject a repeat order for the same checkout).
