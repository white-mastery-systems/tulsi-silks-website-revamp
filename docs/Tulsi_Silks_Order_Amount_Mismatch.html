The website total is the email total divided by about 94.5. That number is currency_type.country_inr_value — rupees per 1 US dollar. $316.32 / 94.5 = $3.35. Shipping $1.75 / 94.5 = $0.018, which rounds to $0.02.

2. Which amount is correct

Correct amount: $316.32. That is the dollar value of this order, and it is the amount Razorpay was asked to charge. $3.35 is a display error. It is not the saree price and it is not the payment amount.

The order is stored in the store currency, INR. A dollar amount is that rupee figure divided once by country_inr_value.

Correct display = stored rupee amount / currency_type.country_inr_value Example: about ₹29,892 / 94.5 = $316.32 Wrong display = $316.32 / 94.5 = $3.35

Why $316.32 is the real order, not $3.35:

  • The email uses this formula once, in priceFormat (yourstore-server/services/common.service.js).
  • Razorpay uses the same formula once, in createRazorpay (yourstore-server/services/create_payment.service.js). The charge is final_price / country_inr_value, currency USD.
  • $316.32 is about ₹29,900. That is a normal Kanjivaram silk saree price, and it sits just under the store’s free-shipping line of ₹30,000, which is why shipping was charged. $3.35 is about ₹316, which is not this product.

Fix the website (Angular). Do not change the backend. Mail and Razorpay already convert once. Changing priceFormat or createRazorpay would change the amount the customer is charged.

The confirmation page loads the raw order from GET /store_details/order_details and then divides every money field by country_inr_value. On this order the page ends up showing that conversion a second time.

5. How the conversion is supposed to work

Catalog price is stored in INR ↓ Checkout saves the order in INR currency_type = { country_code: "USD", html_code: "$", country_inr_value: ~94.5 } ↓ Email and Razorpay divide once → $316.32 ← correct ↓ Website divides that dollar amount again → $3.35 ← bug

country_inr_value is saved when the order is created:

country_inr_value: liveCurrencyDetails.rates[baseCurrency]

baseCurrency is the store currency, INR. On the USD rate row, rates.INR is about 94.5 (rupees for 1 dollar). Product prices are not converted before they are saved. CALC_AC only adds an extra charge percent. It does not divide by the rate.

Rule for the page: show storedAmount / country_inr_value once. The result must equal the email and the Razorpay amount. Do not divide a number that is already in dollars.

10. Fix done in the website code

Repository: tulsi-silks-website-revamp (Angular storefront). The files are the same ones that section 4 lists under YS-Website-Angular. No backend, email or Razorpay code was changed.

Actual root cause: the server render and the browser both divide

The division in getOrderDetails() is correct and runs only once per call. The bug is that the call runs twice on the same data:

Razorpay success → backend redirect → full page load of /checkout/order-summary/product/… ↓ Server render: GET /store_details/order_details → ₹29,892 ↓ Component divides the response object in place → $316.32 ↓ Angular HTTP transfer cache had kept a reference to that same object, and saves it into the page HTML at the end of the render → page ships $316.32 ↓ Browser: component runs again, reuses the saved response ($316.32) and divides again ↓ $316.32 / 94.5 = $3.35 ← wrong
  • Why only Razorpay: Razorpay returns through a server redirect, which is a full page load with a server render. COD goes to the summary page inside the app with no server render, so it divides only once and is correct.
  • Why INR orders look fine: country_inr_value is 1, so dividing twice changes nothing.
